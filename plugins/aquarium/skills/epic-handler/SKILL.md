# Epic Handler

Read [review-routing-contract.md](../../references/review-routing-contract.md) for route selection, route-specific readiness, evidence combinations, recovery, and assessment ordinals. Read [review-intent-contract.md](../../references/review-intent-contract.md) for the shared Review Brief and criterion-level completion assessment. Read [mulgae-review-contract.md](../../references/mulgae-review-contract.md) only when the selected review route is `mulgae`.

Deliver one roadmap epic as a sequence of goal-centered task executions. Own its outcome, order, evidence, and commit boundaries. Select `execute` by default, `plan-only` for a non-mutating plan, `plan-handoff` only when another agent will continue, and `resume` for continuation. Treat "plan only" as `plan-only`; for `plan-handoff` or its resume, read [plan-handoff.md](../../references/plan-handoff.md) and follow it.

Do not invoke `/aquarium:task-handler` or its phase skills; they separately strengthen the procedure around one user-guided task goal. Always read [evidence-residency.md](../../references/evidence-residency.md), [finding-disposition.md](../../references/finding-disposition.md), [release-notes.md](../../references/release-notes.md), [documentation-governance.md](../../references/documentation-governance.md), and [epic-execution-sot.md](../../references/epic-execution-sot.md). On the Podway path also read [procedure-node-contracts.md](../../references/procedure-node-contracts.md).

Use Podway by default. Exclude it only when the current user explicitly opts this epic out before its first managed session starts or a higher-priority instruction prohibits it. For an opted-out epic, do not inspect Podway, load `/use-podway`, or read [podway-integration.md](../../references/podway-integration.md), and do not carry the opt-out into a later workflow.

Otherwise read the Podway contract, then use one `aquarium-goal-v2` session per member-task, pre-validation remediation, or closeout goal and one `aquarium-validation-v2` session for the final epic audit and its audit-scoped remediation. In `plan-only`, create neither goal nor session; in `plan-handoff`, create the first Podway session only after approval, attach the plan, and stop before work. Podway strengthens local execution memory but does not prescribe a phase workflow or replace the roadmap DAG.

Goals below describe workflow objectives. Create a Grok todo list only on explicit user request under its tool contract, whether Podway is active or opted out. Plan approval and a Podway goal do not authorize a Grok todo list. Continue an existing authorized Grok todo list within its own scope and lifecycle; otherwise proceed without one.

## Establish and Approve the Epic

Require one mutable Git repository, one canonical roadmap path inside that repository, and exactly one epic ID present in that roadmap. Reject task-only requests, multiple epics, requests without one canonical roadmap epic identity, and external roadmap authorities. Inspect another repository read-only only when the roadmap explicitly names it; never mutate or create a goal for it.

Before requesting approval:

1. Read repository instructions, the epic, every member task, `docs/README.md`, roadmap and canonical-document links, relevant role owners, required artifacts, explicit dependencies, and any linked active dossier. Resolve the requirement-bearing canonical document set without asking the user for paths. Use the dossier when one exists. When no dossier is declared, assemble the shared composite execution SOT and disclose its source paths and requirement owners in the plan. A declared dossier whose link cannot be resolved is a semantic gap, not dossier absence. Stop and route revision to the appropriate work-definition skill when an exact semantic requirement is missing, ambiguous, or unowned. Otherwise apply the shared dossier-waiver flow. When the work meets a creation threshold, obtain the user's choice to consider a waiver before preparing the final plan; choosing dossier creation stops this workflow with the exact work-definition continuation.
2. Inspect branch, upstream, HEAD, staged, unstaged, untracked, and conflicted state. Separate epic-owned work from existing work and record the starting revision.
3. Discover repository-native verification, Gaori, `/use-gaori`, documentation synchronization, Sanho, `/use-sanho`, lifecycle, commit guidance, and only the prerequisites of each selected review route. Select `mulgae` by default or an explicitly approved `orca`, `native-codex`, or `waived` route for member and whole-Epic checkpoints. Record the exact target, reviewer or waiver authority, and assurance limit. Treat each CLI, repository configuration, project MCP, and agent skill as independent state; a selected-route prerequisite gap never starts another route automatically.
4. Build a dependency DAG. Distinguish member-task edges from pre-epic local or explicit external prerequisites. For every prerequisite record repository, canonical ID, exact revision, lifecycle state, dirty state, evidence, and owner. An incomplete member-task predecessor determines execution order and does not block initial approval. A pre-epic or external prerequisite is satisfied only by committed work at the required revision with verified evidence; if unmet, stop before goal creation or mutation and report the owner and required sequence.
5. Order tasks by dependencies and then roadmap order. Split a cycle only when authority defines pre-validation and finalization; otherwise stop and report its nodes, owners, and missing authority.
6. Preserve successfully terminal tasks, start at the earliest non-terminal task, and retain every task for the final audit. Stop rather than replace a different active goal.
7. Honor an explicit pre-session opt-out without Podway discovery. Otherwise apply the shared contract's readiness and session checks. On degraded readiness, route a missing or unsupported global Podway CLI, daemon, or `use-podway` skill to `/aquarium:dev-setup-global`; route repository configuration or managed-Procedure gaps to `/aquarium:dev-setup`; then stop and ask the user to choose the exact routed repair or an explicit opt-out for this epic.
   - A matching recoverable Aquarium session becomes part of the plan. Only when starting a different session, present the existing session and obtain the shared contract's explicit preserve, lifecycle, delete, or eligible-replace choice. Never route by skill owner or describe the choice as setup repair.
   - A disposed terminal session with verified handoff evidence and a current `session.start_replace` template becomes an exact successor candidate. Include its automatic archival in the epic envelope and, after approval, execute the template's current plain `start` argv without a separate reset before re-observing and beginning the prepared epic session.

Produce one concise, decision-complete epic plan: goal and non-goals, dependency DAG, task order, requirement owners and resolved execution SOT source paths, expected outcomes and commit boundaries, per-task documentation promotion, checks, review targets, lifecycle changes, external handoffs, the active dossier and its repository-defined closeout or the dossier's explicit absence, and known gaps. Avoid unnecessary phase or file mechanics. Preserve the selected mode in every continuation.

Ask once for explicit approval of the plan and execution envelope. When no dossier is declared, require that approval to waive the dossier explicitly; generic approval is insufficient. When the work meets a creation threshold, this is the second confirmation after the user chose to consider a waiver. Approval covers bounded work, shared-policy remediation, checks, the selected review routes and their disclosed source transmission, eligible evidence promotion, scoped staging and one normal completion commit for each planned member Task, exact restaging of affected staged paths, and a disclosed dossier deletion. That approval is the commit-effect authority for each covered member Task after final Goal approval accepts its exact candidate; do not ask again solely because `/aquarium:task-commit` is about to run. It excludes checkpoint or additional commits, commits for a reopened Task, pre-validation or Epic-seam remediation, the final Epic closeout, automatic route changes or waivers, amend, push, PR or release changes, rollout, installation, another repository, unplanned files, unrelated staging, and other destructive actions. A member-Task commit never authorizes upstream publication.

By default the envelope must cover creating or resuming each prepared managed session, the separate fenced `begin`, bounded evidence and decisions, goal revision and rework, terminal completion, supported disposition, and eligible replacement after the authoritative roadmap, commit, review, and worktree evidence is re-read.

`plan-only` stops without mutation. `plan-handoff` also discloses the private temporary plan file, artifact attachment and propagation, running-session stop, exact resume report, and final cleanup. Approval that explicitly omits Podway covers the same envelope without those operations and therefore without plan handoff.

Accept an opt-out only before the first managed-session mutation. Afterward classify every stop or opt-out request through the shared `Handle In-Progress Stop Requests` flow; never assume pause, cancel, reset, or an in-place switch to non-Podway execution. Never mutate a conflicting session automatically.

Do not create a goal, edit files, invoke providers, stage, commit, or alter external state before approval. After approval, `plan-handoff` may perform only its disclosed handoff mutations and must stop before work. Request renewed envelope approval only when the execution SOT source set, requirements, task membership or order, repository scope, product behavior, destructive impact, external actions, or safe diff isolation materially departs from the envelope. Final Goal approval still must accept each exact member-Task candidate and handoff; do not turn that outcome decision into another request for commit-effect authority. Renew the dossier waiver when the revised source set still has no dossier.

When a selected check uses Gaori, read [gaori-integration.md](../../references/gaori-integration.md). Require the agent performing the check to load and follow the installed `/use-gaori` skill before transport selection or execution, then consume the exact command result and evidence through that contract, including prerequisite routing and optional direct-command fallback.

Before each review, bind the effective route to the approved envelope or an explicit later route-change authority. Preserve the prior completed ordinal, assessment kind, finding lineage and dispositions, remaining review authority, and corrected target. Establish one Review Brief containing the named Task, Epic, or remediation goal; actual requirement set and authorities; base revision; exact target; ordered work or correction commits when present; included and excluded paths and artifacts; verification provenance; goal revision; assessment ordinal; assessment kind; mode; and approved scope. Use the same brief for route preflight and execution. Dispatch exactly one selected route: Mulgae through an executing agent that has loaded and follows the installed same-release `/use-mulgae`, Orca through `/aquarium:orca-review` with an explicit reviewer and isolated supported target, native Grok through fresh read-only reviewer subagents on `spawn_subagent` (`background: true`, `isolation: none`, Git-root `cwd`), preferring `aquarium:independent-reviewer` and falling back to `explore`, or waiver through a coordinator assessment of the complete brief. A waiver launches no reviewer and removes neither verification nor the final direct Epic audit.

A completed delegated review or waiver assessment consumes exactly the next ordinal even when it reports findings or a failing Mulgae backend check. An incomplete or failed operation consumes none; native recovery inside the same operation reuses the pending ordinal. Switching after completion uses the next ordinal, while switching after an incomplete operation retains the pending ordinal. Bind the caller-supplied ordinal continuity check to the goal revision, prior and current ordinals, selected mode, and authority. Bind the route check to the immediately preceding route and operation, effective route, requested direction, lifecycle settlement, findings, ordinal, goal revision, and remaining authority; `resume-current` fails when the effective provider differs from the preceding unsettled provider. Preserve route-specific evidence and never fabricate a run, publication, findings query, capture, or native digest. On failure, stop for explicit `resume-current`, `switch-route`, `waive`, or `stop`; active or uncertain native work must first reach a safe state through its owner, and no route changes automatically.

## Complete Task Goals

For each non-terminal task in order:

1. Reconfirm every member-task predecessor is successfully terminal with its required commit and evidence, and recheck any pre-epic or external prerequisite at its exact revision. Stop on a gap; otherwise establish the task ID and required outcome. When a Grok todo list is explicitly authorized, create one or continue the matching existing goal under its tool contract, and omit a token budget unless the user supplied one.
2. Work from current authority and code toward the task goal. Choose the implementation, investigation, documentation, and verification sequence that best fits the repository and task; do not manufacture phase artifacts or pause for routine choices already inside the approved envelope.
3. Implement the complete task outcome, including runtime wiring, tests, generated or derived artifacts, canonical specifications, architecture, decisions, implementation tips, operations and public usage where affected, current guidance for later tasks in the resolved execution SOT, and roadmap state that the authority requires. In an enrolled repository, include one concise release-note `entry` for a shipped outcome or record `intentional no-note` before review; otherwise record `not-enrolled`. Preserve unrelated work.
4. Run proportionate repository-authorized checks. Focused green checks prove only mapped requirements; forbidden or unavailable database, E2E, live, or broad gates remain explicit evidence gaps and are never run merely because another workflow normally would.
5. Run no more than three `work-unit` assessments and one `remediation-confirmation` on the latest member-task target. Each `work-unit` brief names the Task objective and criteria, base revision, exact candidate, ordered work commits when present, task-owned staged, unstaged, untracked, generated and derived files, excluded state, and verification evidence. A committed Epic candidate may use an exact Orca `HEAD`, commit, or range target; an uncommitted member-task candidate must satisfy the same isolated `staged` rule as Task delivery. Ordinals one through three are `remediation-eligible`; ordinal four is `confirmation-only`. Stop after any clean result or completed Low-only settlement, because unused budget is not a reason to run another assessment.
   - Stop delegated review when route-specific readiness passes, no finding needs confirmation, no effective Medium-or-higher finding remains, and every finding in the frozen eligible Low set can be settled under the shared contract. Preserve the historical Low count, complete dispositions and local verification, then assess the goal without another delegated review. If confirmation requires a check outside the approved epic envelope, leave the decision unset and ask for bounded confirmation authority. Reclassify the same finding as `Valid` or `Invalid`, manually rework `record-evidence`, and evaluate the decision again without consuming another review ordinal unless the selected review runs again.
   - After first- or second-round findings, verify them as hypotheses and reprioritize them. Fix every valid in-scope Medium-or-higher issue and rerun affected checks. When only eligible Low findings remain, freeze and settle that finite set with required local checks or canonical future-work owners and do not run another review solely for Low.
   - After the third `work-unit` assessment, freeze the remaining correction set. Its correction receives one ordinal-four `remediation-confirmation` restricted to the source finding IDs, correction commits or capture delta, invalidated criteria, directly affected callers, contracts and tests, and correction-caused regressions. Carry unaffected criterion assessments only when current evidence proves they remain valid. A material objective, requirement, or changed-surface expansion stops for an explicitly approved new goal revision or work-unit assessment rather than broadening the confirmation.
   - After ordinal four, any Medium-or-higher or completion rework stops at a fresh `choose-user-direction` attempt. The user's `fix-and-review` decision authorizes only its one transition back to work and one next-ordinal remediation confirmation; if that confirmation still establishes rework, stop at the new unset decision and ask again. Ordinary Low settlement remains available for every route. Only Mulgae may defer a small independent Low future risk through promoted `hardening-deferral` evidence, because that path requires an exact run, finding membership, committed publication, successful query, and authoritative native target digest; it does not create a review round. Orca, native Grok, and waiver evidence record that no promoted hardening evidence applies.
   - Reconstruct member ordinals and assessment kinds from verbose goal Procedure history for the current revision and exact selected-route evidence references; only Mulgae requires effective root or composite run IDs with verified original-root lineage. Preserve the count across rework and resumption. An unprovable ordinal stops before review. Never silently run a later review, return to a work-unit assessment, or defer stale evidence.
6. Treat the member task as review-approved only when the selected operation is complete or waived, its route-specific evidence combination is valid, workflow verification passes, every actual requirement has a conservative completion assessment with zero `unmet` or `unverified` criteria, every Medium-or-higher finding has corrected-target assessment evidence, and every finding in the frozen eligible Low set has a completed shared disposition with passing required local verification on the exact current target, zero pending dispositions, and no current blocker. Mulgae additionally requires passing CI, committed publication, complete coverage, and a successful findings query; Orca, native Grok, and waiver require `backend-check-result=not-provided`. Zero findings, reviewer success, or process exit alone is insufficient.
   Keep operational evidence, confirmation, completion, finding class, rework authority, and Low handling in their declared serial routing chain. Evaluate finding-count consistency as a guard axis of the finding-class decision, and mark it consistent only when the unresolved total equals the Medium-or-higher plus Low buckets. Do not reconstruct a combined rework total or move one decision's predicates into another gate. Record hardening-deferral state only after a consistent Low-only finding classification; clean evidence proceeds without manufacturing a deferral record.
   Record `structured_extraction_status` independently as `structured`, `mixed`, or `reports_only`. `reports_only` is not itself a failure and does not replace or relax any completion condition above; the accepted reports remain authoritative, and every extracted finding remains an advisory hypothesis that requires local verification.
   - The sole member-task exception is a complete ordinal-two work-unit assessment whose remaining valid Low-only findings are classified at `decide-evidence`, fully recorded at `record-hardening-deferral`, and selected through `decide-low-handling: defer`. Do not call that task review Mulgae-complete or allow the exception at final epic validation.
7. Move the task to its defined successful state and prepare the exact isolated task-owned candidate and handoff. Record its assessed Goal outcome, then obtain final Goal approval for the exact diff, lifecycle and record decisions, release-note target and exact `entry` text or non-entry decision, review evidence, and remaining handoffs. Treat `changes-requested` as rework before any commit; the member-Task commit authority remains unused. Any candidate change after approval makes that outcome approval stale.
8. After final Goal approval, hand the approved candidate, that outcome approval, task ID, the carried one-commit authority from the unchanged Epic envelope, `review-route`, `review-operation`, `review-evidence-reference`, `backend-check-result`, `assessment-provenance`, the consumed `assessment-ordinal` and `assessment-kind` or their explicit inapplicability, the waiver summary or explicit inapplicability, the complete Low-settlement composition defined by the shared finding-disposition contract or its explicit inapplicability, and either an explicit absence or the live deferral IDs, committed publication, successful findings query, exact finding membership, authoritative native target digest, and promoted manifest path and digest to `/aquarium:task-commit`. Do not ask for another commit approval when the handoff remains current and complete. Record the resulting commit SHA during Podway closeout. Complete an authorized Grok todo list only after its full objective is achieved, its required commit exists, its evidence trailer and package match the handoff when applicable, no task-owned residue remains, and unrelated work is unchanged; then re-read roadmap, DAG, Git state, and evidence before advancing.

With Podway active, run `podway observe --json --wait-for-idle` before each bounded work delegation and verify the expected Procedure ID, canonical goal identity, session, lifecycle, revision, and, when running, its attempt, goal revision, and current node. A plan-handoff goal additionally requires the shared artifact verification before any work delegation.

Start or resume the matching prepared goal procedure only after approval, re-observe and `begin` it before work, coordinate with an explicitly authorized Grok todo list under the shared Podway contract, and independently verify returned native evidence before recording it. In `plan-handoff`, attach the approved plan and stop with required work items unset; on resume and every successor session, reattach the same verified artifact before work. Only then select decisions and assess criteria through actions allowed by `guidance.allowed_actions` and represented by current `mutation_templates` entries.

After step 8, complete the Podway session, verify its terminal outcome, and repeat the handoff checks. Record `handed_off` with the exact task commit SHA. When another member task remains, use the fresh eligible replacement template to atomically create its prepared session and re-observe before `begin`; after the final member task, leave the disposed terminal session for the audit transition below. Never replace a failed, non-terminal, undisposed, or insufficiently evidenced session.

Use a fresh read-only subagent for an additional perspective when task risk or uncertainty merits it. Keep that optional perspective distinct from a selected `native-codex` checkpoint, and do not count it as delegated evidence unless the approved route, complete brief, exact target, and fresh host delegation establish it. `/aquarium:independent-review` is the standalone native-subagent entrypoint; do not invoke it inside a handler flow, and invoke `/aquarium:orca-review` only through an explicitly selected authorized route. Do not let either impose the `/aquarium:task-handler` phase workflow.

Keep implementation, verification, review target, lifecycle, commit, publication, and live evidence distinct. Post-review changes to code, tests, canonical documentation, or product artifacts stale affected evidence; only planned status transitions and independently checked promoted-evidence projections do not. A completed Low correction stays stale: record that its review predates the corrected bytes, then advance only after its shared disposition and required local checks. Do not advance with an incomplete required gate or evidence.

## Audit and Remediate the Epic

After all tasks are terminal, audit the latest committed epic state without source mutation. Build a requirement-to-owner-to-production-to-test-to-document matrix across every task and inspect integration seams, consumers, persistence, concurrency, migrations, generated artifacts, recovery, operations, and roadmap consistency.

- Before a whole-epic review, verify every member-task `Aquarium-Evidence` manifest and payload without local runtime. Load findings only for `hardening-deferral`; retain other purposes for named consumers. Use an available exact run for legacy `Mulgae-Deferred-Run` and `Mulgae-Deferred-Finding` trailers. When that run is gone, do not promote it: record an evidence gap and cover its paths and current requirements in the current remediation-eligible whole-epic audit. Podway and trailer prose never replace evidence.
- Revalidate each deferred finding against the latest epic snapshot when its native evidence remains available. Otherwise use the promoted ID, disposition, and affected paths only to scope fresh whole-epic audit coverage; do not claim finding-level equivalence from the package. Remediate every issue established by current evidence and explicitly record unavailable, invalid, or resolved prior findings. This reconciliation and its local verification do not consume an epic review round and do not invoke a Mulgae child workflow.
- Then run no more than three whole-Epic `work-unit` assessments and one `remediation-confirmation` through the selected route. Each work-unit brief names this Epic, its member and seam criteria, base and candidate commits, ordered remediation commits when present, changed paths and artifacts, excluded state, and verification evidence. Record the route-neutral operation, evidence reference, backend check, provenance, next ordinal, assessment kind, criterion-level completion assessment, reported severity, effective priority, validity, and disposition in the Validation Procedure. Keep direct-audit and reviewer or waiver finding namespaces separate. Stop immediately when the route-specific evidence is valid, workflow verification passes, the assessment is clean, and no completion criterion is `unmet` or `unverified`. Route owned gaps through the existing remediation owner. Complete Low dispositions locally without consuming another assessment.
  At final review, admit the operation result, finding confirmation, completion state, required evidence, and applicable blocker state through separate serial decisions before selecting Low settlement or validation. The review mode is evaluated only after rework has been established, so confirmation-only evidence cannot silently enter remediation.
- After third-round fixes, restrict the direct re-audit and ordinal-four review to the frozen correction set and direct regression surface, then run one `confirmation-only` remediation confirmation. Complete eligible Low dispositions locally. If a valid Medium-or-higher finding remains, select the supported `user-direction` classification, record only the exact issue set and exhausted authority at `await-user-direction`, complete that action, and stop at `choose-user-direction` with its decision unset. Ask the user to authorize one additional fix-and-confirmation budget or stop; do not fix, review, accept, or defer the risk before the answer.
- Reconstruct ordinals from the current goal revision's verbose Validation Procedure history and exact route evidence references; for Mulgae, verify original-root lineage. Never use `latest`, infer an identity, or reinterpret an older Procedure snapshot. An unprovable ordinal stops before another review.
  Preserve the count and assessment kind across rework and resumption, resetting only for an explicitly approved new goal revision. After an authorized extra budget, remediate through the owning audit route and run exactly one next-ordinal remediation confirmation; if it still finds valid issues, ask again rather than restoring an unbounded loop.

With Podway active, atomically replace the disposed last-task session with a prepared `aquarium-validation-v2` session, then re-observe and `begin` the final audit. For a plan handoff, attach and verify the same artifact at the validation baseline before audit work. Record operational result, total confirmed count, confirmation count, current blockers, eligible Low gaps, and remaining blocking-rework authority separately. Route only blockers with current authority through remediation and re-audit. Route Low-only audit or re-audit evidence through `record-audit-low-basis` to the independently required final review without broad remediation. At final review, retain audit and provider identities under separate namespaces and route from pending applicable Low dispositions, current applicable blockers, and required evidence gaps; a clean provider count cannot erase an applicable audit Low set. Record remediation scope at the active validation session's `remediate` node. Create a separate Grok todo list only on explicit user request under its tool contract; do not create nested Podway sessions.

After the validation session succeeds, use `handed_off` only when an exact authoritative external result already exists. Otherwise record `not_required` only after verifying that the same approved epic execution continues and the closeout session requires the slot. Atomically replace the disposed validation session with the prepared closeout goal and `begin` it.

Classify each verified gap by canonical requirement owner, not file count or edit location:

- A violation owned by one task remains task-owned even if that task is Completed or the fix crosses modules. Create a new goal for that task, transition through the roadmap's reopen state and back to success when one is defined, obtain fresh verification and selected-route evidence, and hand the isolated correction to `/aquarium:task-commit` under its task ID.
- An epic seam invariant owned by no single task is cross-task. Create an epic remediation goal and hand the isolated correction to `/aquarium:task-commit` under the epic ID.
- Work requiring another repository is external. Stop with its owner, exact revision, and missing evidence; do not edit it.

If ownership is ambiguous, stop before goal creation and report the missing authority. Process task-owned gaps in canonical task order, then cross-task gaps. After remediation before any of the first three work-unit assessments, refresh the complete Epic audit. After the third work-unit assessment, re-audit only the frozen correction set, invalidated criteria and direct regression surface. When an external blocker is resolved, first revalidate the DAG at its new exact revision; restart a work-unit audit only when the resolved dependency changes the authorized objective or requirement surface.

Only after the audit, required selected-route evidence, all Medium-or-higher corrections and confirmations, and the complete verified finite Low settlement support validation may one final epic closeout goal be created. Classify remaining execution-SOT content and stop on unowned durable information. In one epic-ID diff, update required owners and lifecycle state. When a dossier exists, inventory every canonical roadmap reference to it, update only this epic's link, and retain the shared dossier while another consumer epic remains non-terminal or still canonically references it.

Delete a dossier only at the last consumer closeout under the repository lifecycle and approved deletion envelope. When no dossier exists, manufacture no documentation diff. Verify task-ID resolution and affected links, then synchronize and hand any required diff to `/aquarium:task-commit`.

For this final closeout goal only, record `goal-kind=epic-closeout`, `review-evidence-kind=validated-closeout`, select `closeout-not-required`, omit the review ordinal and run ID, and bind both typed operation results and the evidence summary to the successfully terminal validation session plus focused closeout checks. Record other goals as `member-task` or `pre-validation-remediation`. Never use this exception for either of those goal kinds, and never report no-change while this epic's repository-required dossier closeout remains; retaining a correctly linked shared dossier is not residue.

- Complete the closeout Podway session after verifying the commit or explicit no-change result. Record `handed_off` only for an authoritative closeout commit; when no final repository result is required, record `not_required` with the verified no-change reason even if earlier remediation commits exist. Leave the final terminal session intact.

## Hand Off Commits and Report

Each `/aquarium:task-commit` handoff includes repository, roadmap, work-unit ID, lifecycle and record decisions, release-note decision, isolated scope, verification evidence, `review-route`, `review-operation`, `review-evidence-reference`, `backend-check-result`, `assessment-provenance`, the consumed `assessment-ordinal` and `assessment-kind` or their explicit inapplicability, the waiver summary or explicit inapplicability, the complete Low-settlement composition defined by the shared finding-disposition contract or its explicit inapplicability, zero or more promoted manifest path and digest pairs or their explicit absence, and one-commit authority. A normal planned member-Task completion cites the approved Epic envelope as its commit-effect authority and final Goal approval as acceptance of the exact candidate. Reopened-task corrections, pre-validation and Epic-seam remediation, final closeout, checkpoints, and additional commits require direct one-commit authority. A hardening handoff also includes its exact Mulgae run and finding IDs, committed publication, successful findings query, exact finding membership, and authoritative native target digest; other routes state that no hardening evidence applies. That skill owns staging, Lore and Sanho checks, commit execution, hook reconciliation, and snapshot verification. Never commit independently, ask for redundant commit approval, amend, or infer push authority.

Use `/use-sanho` directly only for separately authorized synchronization outside the commit boundary. Use its refreshed push workflow only for a separately authorized push. Commit and upstream publication remain separate states.

Do not create or read `.aquarium` or other shadow state. Resume from roadmap, Git history and worktree, current goal, recoverable approval, repository evidence, and the selected route's exact evidence; a recorded plan handoff also requires its exact session-bound artifact. Preserve the exact review lineage, frozen Low set, completed dispositions, pending count, and consumed one-pass authority. Never create a replacement review or reset a budget to reconstruct lost narrative context. Request fresh approval when the envelope cannot be recovered.

At every stop and final handoff report current task and epic, dependency changes, completed and remaining goals, commits and roadmap states, checks and evidence gaps, selected route, operation, evidence reference, provenance, backend-check result, any route-specific lifecycle status, worktree boundaries, upstream publication state, and the exact next safe action. For a waiver, also report `review waived`, its authority and reason, and the resulting assurance limitation; never present it as delegated review. A plan handoff must also report every session and artifact identity required by the shared reference.
